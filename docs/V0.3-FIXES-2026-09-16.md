## R1 — TLS 单元测试不再泄漏 TCP

位置：`third_party/async-tls/src/identity_test.mbt`。

`accept_server` / `connect_client` 原来只把 TCP 交给 `Tls` 包装后就丢弃句柄，
而 `Tls::close()` 不负责关闭底层流；握手失败和超时路径同样没有清理。现在两个
辅助函数返回 `TestConnection`（同时持有 `tls` 和 `tcp`），构造失败时用
`errdefer tcp.close()` 兜底，每个测试作用域用 `defer connection.close()` 按
“先 TLS、后 TCP”的顺序释放。

复跑（`MOONBIT_ASYNC_CHECK_FD_LEAK=1`）：

| 命令 | 结果 |
|---|---|
| `moon test --package Strangelight-Merser/async-tls --filter 'tcp mtls handshake with client identity'` | 1/1 通过，无泄漏 |
| `moon test --package Strangelight-Merser/async-tls` | 12/12 通过，无泄漏 |
| `moon test`（整个 workspace） | 39/39 通过，无 `file descriptor leak detected` |

修改前单例稳定报 2 个 Socket，全套报 17 个并以 SIGABRT 结束（本轮复现）。
另外在独立 `ubuntu:24.04` x86_64 容器（Docker 模拟）中用固定工具链复跑：12/12、
39/39 均通过；把 `TestConnection::close` 里的 `self.tcp.close()` 去掉作为反例，
两处都稳定报 12 个 Socket 泄漏并退出 255，恢复后重新通过，说明通过不是空信号。
同一修复已同步到相邻独立仓库 `moon-async-tls`，两边源码逐一比较无差异。

## R2 — 演示与场景冒烟按真实 workspace 产物定位

位置：新增 `tests/build_paths.py`；`tests/scenario_smoke.py`、`examples/mqtt_demo/demo.py`。

两个入口原来硬编码 workspace 之前的扁平路径
`_build/native/debug/build/examples/mqtt_demo/...`。新增的解析器以 `moon.mod`
的模块名和 `moon.work` 是否存在推导布局：

- 有 `moon.work`：
  `_build/native/debug/build/Strangelight-Merser/moon-mqtt-client/examples/mqtt_demo/<pkg>/<pkg>.exe`
- 无 `moon.work`：回退扁平路径，并支持无 `.exe` 后缀的工具链。

用 `moon.work` 判断而不是“目录是否存在”，避免旧 `_build` 掩盖问题或运行到上个
版本的二进制。解析器不会跨布局回退：当前布局没有产物时直接返回期望路径并由调用
方报错，不会去捡另一种布局遗留的旧程序。

复跑：在排除 `_build`、`.tools`、`.venv`、`.git` 的独立源码副本中
`moon build --target native`，产物只出现在带命名空间的路径下；随后

| 命令 | 结果 |
|---|---|
| `python tests/scenario_smoke.py` | 通过，退出 0 |
| `python examples/mqtt_demo/demo.py` | normal / lost_puback / broker_restart / controller_restart 全部 PASS，退出 0 |

Linux 侧在独立容器中复验：干净构建后磁盘上只有
`_build/native/debug/build/Strangelight-Merser/moon-mqtt-client/examples/mqtt_demo/...`，
不存在扁平目录；`scenario_smoke.py` 与四场景 `demo.py` 均退出 0。无 `moon.work`
的模拟根目录解析到扁平路径。

## R4 — TLS 1.3 身份拒绝保留 `TlsFailure` 类别

位置：`client.mbt`（`client_error_of`）、`runtime.mbt`（`dial` 首连读写分类）；
回归测试
`tests/integration/run.py::test_mtls_tls13_only_identity_rejection_error_types`、
`tests/integration/run.py::test_tls_clean_close_without_alert_is_tls_failure`。

TLS 1.3 下服务端对客户端身份的拒绝可以在客户端 TLS 构造返回之后，才在首次
MQTT CONNECT 写或 CONNACK 读时以 `@tls.TlsError` 出现。`client_error_of` 的
兜底分支把它降级为 `ProtocolError`。现在增加
`@tls.TlsError(msg) => TlsFailure(msg)`，在首连路径保留文档约定的
`TlsFailure`；身份加载类错误仍由 `dial` 的既有转换归为 `InvalidConfig`。

独立复现（TLS 1.3-only、要求客户端证书的 Mosquitto，公开 API 观测）：

| 客户端身份 | 修复前 | 修复后 |
|---|---|---|
| 未提供证书 | ProtocolError | TlsFailure |
| 不受信 CA 签发 | ProtocolError | TlsFailure |
| 已过期 | ProtocolError | TlsFailure |
| 错误服务器 CA（对照） | TlsFailure | TlsFailure |

新增用例对上述条件断言公开错误类型，而不是只看非零退出码；同时把
`test_mtls_tls13_only_qos1_roundtrip` 末尾的拒绝用例也改为断言 `TlsFailure`。

同一类型问题还有一条“干净关闭”路径：对端在本地握手返回后只发送 close_notify
（或直接关闭传输），不发送致命告警时，客户端会以关闭的 reader 结束，而不是
`@tls.TlsError`。为此在 `dial` 的首次 CONNECT 写与 CONNACK 读外包一层分类：TLS
模式下把 `@io.ReaderClosed` / `@tls.ConnectionClosed` 也归为 `TlsFailure`；明文
连接不受影响。新增用例 `test_tls_clean_close_without_alert_is_tls_failure` 用
TLS 1.3 服务端握手后干净关闭来复现，去掉该分类时会稳定得到 `ProtocolError`，
说明用例有区分度。

## 附：EMQX 互操作的 Linux 权限与失败清理

位置：`tests/emqx_interop.py`。

EMQX 5.8.8 容器以 uid/gid 1000（`emqx`）运行，而宿主 PKI 目录由
`tempfile.mkdtemp` 建成 0700、`server.key` 又被设成 0600。Linux 宿主上
bind mount 保留宿主 uid（不等于 1000），因此容器用户既不能进入目录也不能读
服务端私钥，mTLS 监听无法建立；macOS 的 Docker Desktop 不校验挂载权限，所以
此前只在 macOS 通过。改动：

- `EmqxMtls` 把证书目录设为 0755、`server.key` 设为 0644（EMQX 只需读它），
  客户端私钥仍为 0600；`Emqx` 的挂载目录同样设为 0755 以便容器读取
  `acl.conf`（公开规则文件）。
- 两个容器类都增加 `_remove_container()`，`start()` 先清理同名残留容器，
  `close()` 复用它；测试的 `setUp` 改为**先** `addCleanup(close)` 再
  `start()`，这样启动失败也会清理容器，不再因残留名字导致下次冲突。
- `Emqx.close()` 不再遗留临时目录。

复跑：

- macOS：`python tests/emqx_interop.py` **4/4 通过**，无残留容器。
- Linux 语义（把同一 PKI 放进 Docker volume，即 Linux 文件系统，权限在访问时
  生效，文件属主为 root≠1000，等价于 CI runner 的 bind mount）：
  - 旧权限 0700/0600：EMQX 记录
    `cert_file_not_found ... server.key/server.pem/client-ca.pem`，
    `Failed to start listener ssl:default on :8883`，容器 `Exited (1)`，mTLS
    连接被拒。
  - 新权限 0755/0644：`Listener ssl:default on :8883 started.`、
    `EMQX 5.8.8 is running now!`，Paho mTLS 连接成功（带客户端证书），
    不带客户端证书被拒；客户端私钥仍为 0600，uid 1000 读取报
    `Permission denied`。

`_remove_container` 也被验证能删除同名冲突容器，且 unittest 在 `setUp` 失败时
仍会执行已注册的 cleanup。

## 评审确认的既有边界（不在本轮 R1–R4 范围）

独立评审另外指出两处先于本轮存在的错误分类细节，本轮未改：

- `connect_timeout_ms` 在 TLS 握手阶段到期时，`dial` 的转换会把超时归为
  `TlsFailure`/`InvalidConfig`，而明文 TCP 超时落到 `ProtocolError`；现有
  `test_mtls_handshake_timeout_then_new_client` 只断言非零退出与耗时。
- 不可读的 `CustomCA` 信任文件被归为 `TlsFailure`，而 `docs/API-CONTRACT.md`
  把“文件缺失/不可读”归入 `InvalidConfig`；无对应测试。

两处都未出现在再次验收的 R1–R4 中，若要收敛错误契约，建议下一轮单独补分类与
断言，避免与本轮资源清理、路径定位和注册表入口修复混在一起。
